## 1. Executive Summary & Governance Intent

The MechAI platform has successfully constructed and validated the physical and structural foundations of its technical manual ingestion pipeline:
- **RFC-001 / RFC-002 / RFC-003**: System architecture, domain models, and canonical automotive ontology.
- **RFC-004 / RFC-005**: High-throughput Stage 1 PDF parsing and real-world Suzuki manual validation.
- **RFC-006 / RFC-007 / RFC-008**: The Document Intelligence Layer, delivering Stage 2.0 Geometric Layout Zoning (`LayoutCIR`) and Stage 2.1 2D Spatial Topological Reading Order (`OrderedLayoutCIR`).

A critical architecture review evaluated the system against the horizon of ingesting **100,000+ to 1,000,000+ OEM workshop manuals**. That review revealed both the foundational brilliance of the decoupled, contract-driven design and several systemic scalability constraints, assumption boundaries, and latent technical debts.

**The mission of RFC-008.5 is to establish an authoritative Architecture Freeze.**

Before Phase 3 (Automotive Domain Extraction: Procedures, Torque Matrices, Wiring Diagrams, SSTs, DTCs, and Causal Knowledge Graphs) commences, this RFC:
1. **Freezes foundational contracts** to prevent downstream churn.
2. **Defers valid post-MVP architectural extensions** to keep engineering velocity focused.
3. **Specifies mandatory pre-Phase 3 refactors** that pose genuine architectural blockers.
4. **Catalogs a prioritized Technical Debt Register** with impact, effort, and target milestones.
5. **Establishes the Future RFC Roadmap** (RFC-018 through RFC-023).
6. **Delivers the formal Phase 3 Readiness Verdict**.

## 2. Core Architecture Freeze

The following architectural models, contracts, and protocols are declared **FROZEN**. They represent mathematical truths of coordinate geometry, typographical primitives, and graph topologies. No breaking changes may be introduced to these contracts during Phase 3 or Phase 4.

### 2.1 Frozen Contracts & Data Structures

| Contract / Symbol | Module | Immutability Rationale |
| :--- | :--- | :--- |
| `BoundingBox` | `mechai.contracts.provenance` | Defines exact 2D axis-aligned Euclidean geometry ($[x_0, y_0, x_1, y_1]$) in Adobe PDF point space ($72\text{ pt/inch}$). Universal coordinate primitive across all 16 stages. |
| `SourceRef` | `mechai.contracts.provenance` | Grounding anchor connecting every extracted entity to its page number, bounding box, extraction method, and epistemic confidence. Breaking this breaks the audit chain. |
| `ExtractionMethod` | `mechai.contracts.provenance` | Enum classifying provenance mechanisms (`RULE`, `HEURISTIC`, `LLM`, `DOCLING`, `OCR`). Additive extension only. |
| `ParsedWord` | `mechai.contracts.scrubbing` | Ground-truth typographical token containing exact coordinates, point size, font family, bold, and italic flags. Physical extraction output. |
| `ParsedImage` | `mechai.contracts.scrubbing` | Ground-truth raster/vector image anchor with page bounding box, pixel dimensions, format, and optional artifact file path. |
| `ParsedPage` | `mechai.contracts.scrubbing` | Immutable container of raw page tokens, images, and physical dimensions. |
| `ParsedDocument` | `mechai.contracts.scrubbing` | Stage 1 output contract. Immutable container of all parsed pages and source path. |
| `RegionType` | `mechai.contracts.layout` | Closed set of 16 spatial and semantic region classifications. Universal across technical documentation. |
| `ColumnGutter` | `mechai.contracts.layout` | Mathematical representation of vertical whitespace gutters identified by projection profiles. |
| `PageMargins` | `mechai.contracts.layout` | Calculated page margin boundaries ($[L, T, R, B]$). |
| `LayoutRegion` | `mechai.contracts.layout` | Spatial region containing unique ID, bounding box, page index, classified `RegionType`, consolidated text, reading zone ID, and column index. |
| `PageLayoutCIR` | `mechai.contracts.layout` | Complete single-page layout CIR containing margins, header/footer zones, column gutters, and classified layout regions. |
| `LayoutCIR` | `mechai.contracts.layout` | Stage 2.0 output contract aggregating `PageLayoutCIR` structures for the entire document. |
| `FlowEdgeType` | `mechai.contracts.ordering` | Closed set of 10 reading order transition types (`NaturalFlow`, `ColumnWrap`, `SpanningDescent`, `SpanningAscent`, `CaptionLink`, `CalloutAside`, `SidebarBranch`, `CrossPageFlow`, `HeaderAttachment`, `FooterAttachment`). |
| `ReadingFlowType` | `mechai.contracts.ordering` | Macro-classification of page flow (`SingleColumn`, `MultiColumnWrap`, `SpanningInterleaved`, `SidebarInterrupted`, `ComplexIrregular`). |
| `ReadingOrderEvidence` | `mechai.contracts.ordering` | Explainable decision record containing deterministic rule ID, source/target zones, spatial distance, confidence, and human-readable rationale. |
| `ReadingOrderNode` | `mechai.contracts.ordering` | Graph node mapped 1:1 to a `LayoutRegion`. |
| `ReadingOrderEdge` | `mechai.contracts.ordering` | Directed edge between reading nodes with typed flow classification, confidence, and explainability evidence. |
| `AlternativeReadingPath`| `mechai.contracts.ordering` | Formal representation of non-linear reading traversals (e.g., aside boxes, safety sidebars). |
| `ReadingOrderGraph` | `mechai.contracts.ordering` | Directed Acyclic Graph (DAG) possessing verified topological sortability and strict acyclicity. |
| `OrderedLayoutRegion` | `mechai.contracts.ordering` | Enriched `LayoutRegion` possessing 1-based reading sequence index, reading depth, and primary flow flag. |
| `OrderedPageCIR` | `mechai.contracts.ordering` | Complete single-page ordered CIR containing ordered regions, the page DAG, primary sequence, and flow categorization. |
| `OrderedLayoutCIR` | `mechai.contracts.ordering` | Stage 2.1 output contract providing the unified, human-reading-ordered Canonical Intermediate Representation for Phase 3 extractors. |

### 2.2 Why These Contracts Must Never Change
1. **Downstream Decoupling**: Phase 3 extractors (Procedures, Torques, Tools, DTCs) depend exclusively on `OrderedLayoutCIR`. Freezing `OrderedLayoutCIR` guarantees that Phase 3 development will never experience upstream schema breakage.
2. **Mathematical Invariance**: A bounding box, a font size, a column gutter, and a directed graph edge are invariant mathematical structures. They do not change whether processing a 1994 Toyota Supra manual, a 2024 Tesla Model 3 manual, or a Boeing 737 AMM.
3. **Sub-Pixel Auditability**: Preserving `SourceRef` immutability ensures every fact generated in Phase 4 is traceable back to the source PDF byte stream.

## 3. Deferred Architecture (Post-MVP Scope)

To maintain focus on delivering the core automotive intelligence MVP, several advanced capabilities identified in the architecture review are **explicitly and intentionally deferred**.

```
+----------------------------------------------------------------------------------------------------+
|                                  DEFERRED ARCHITECTURE MATRIX                                      |
+----------------------------------------------------------------------------------------------------+
|  Item                      | Target Milestone | Deferral Justification                             |
+----------------------------+------------------+----------------------------------------------------+
|  Optical Character Recog.  | v1.2 (RFC-018)   | 90%+ of target OEM manuals (2000-2026) are digital  |
|  (OCR Fallback Engine)     |                  | vector PDFs. OCR adds heavy CUDA/Tesseract weight. |
+----------------------------+------------------+----------------------------------------------------+
|  Non-PDF Ingestion         | v1.3 (RFC-019)   | Primary OEM service documentation is distributed   |
|  (HTML / XML / SGML)       |                  | as PDF. Web scraping adapters belong in v1.3.      |
+----------------------------+------------------+----------------------------------------------------+
|  Distributed Processing    | v2.0 (RFC-020)   | Single-node batch processing handles up to 10K     |
|  (Ray / Celery / Kafka)    |                  | manuals. Distributed orchestration is post-MVP.    |
+----------------------------+------------------+----------------------------------------------------+
|  Multi-Language Support    | v2.0 (RFC-022)   | MVP target market is English-language service      |
|  (DE / JA / FR / ES / ZH)  |                  | documentation. Multilingual NLP deferred to v2.0.  |
+----------------------------+------------------+----------------------------------------------------+
|  Streaming Disk-Backed CIR | v1.4 (RFC-023)   | Target manuals average 100-800 pages. Memory is    |
|  (Page-by-Page Spill)      |                  | manageable within 16GB RAM for single-manual runs. |
+----------------------------------------------------------------------------------------------------+
```

### 3.1 Detailed Deferral Rationale

#### 3.1.1 Optical Character Recognition (OCR Fallback)
- **Status**: Deferred to **RFC-018 (v1.2)**.
- **Rationale**: Modern automotive workshop manuals from major OEMs (Toyota, Honda, Ford, GM, VAG, BMW, Hyundai) published after 2000 are digitally authored vector PDFs. `PyMuPDFParser` extracts native character streams with sub-millisecond per-page latency. Adding an OCR subsystem (Tesseract, PaddleOCR, or Surya) introduces massive binary dependencies, multi-second latencies per page, and GPU requirements that are unnecessary for the initial MVP corpus.

#### 3.1.2 Non-PDF Document Ingestion (HTML/XML Adapters)
- **Status**: Deferred to **RFC-019 (v1.3)**.
- **Rationale**: While BMW TIS and Tesla Service operate web portals, 95% of independent repair shops, aftermarket aggregators (AllData, Mitchell1), and OEM downloads provide standalone PDF manuals. Creating dedicated DOM scrapers and SGML/XML parsers at this stage would divert resources away from core automotive knowledge extraction.

#### 3.1.3 Distributed Pipeline Orchestration (Ray / Celery / Kafka)
- **Status**: Deferred to **RFC-020 (v2.0)**.
- **Rationale**: A single 32-core workstation or cloud instance running multiprocessing workers can parse and process ~500 manuals per day. At the current MVP development stage, pipeline correctness, ontology grounding, and extraction precision take absolute precedence over horizontal scale-out infrastructure.

#### 3.1.4 Multilingual Intelligence (i18n & Non-Latin Typography)
- **Status**: Deferred to **RFC-022 (v2.0)**.
- **Rationale**: English is the universal standard for global automotive technical service documentation. Broadening regexes and NLP classifiers to handle German (`WARNUNG`), Japanese (`警告`), or French (`ATTENTION`) adds localized linguistic complexity that can be isolated into localized modular rule packs in v2.0.

#### 3.1.5 Disk-Backed Streaming CIR Storage
- **Status**: Deferred to **RFC-023 (v1.4)**.
- **Rationale**: Standard workshop manuals range from 80 to 1,200 pages. In-memory `ParsedDocument` and `OrderedLayoutCIR` structures for an 800-page manual consume ~180MB RAM. While 5,000-page mega-manuals exist (CAT SIS), streaming disk-backed object stores can wait until large-scale commercial batch indexing begins.

## 4. Mandatory Refactors Before Phase 3

The following refactors address structural risks identified in the architecture review. These are **strictly localized fixes** to existing components and do not change public contract signatures or stage interfaces.

```
+----------------------------------------------------------------------------------------------------+
|                                MANDATORY PRE-PHASE 3 REFACTORS                                     |
+----------------------------------------------------------------------------------------------------+
|  #  | Refactor Target          | Current Implementation    | Target Resolution                     |
+-----+--------------------------+---------------------------+---------------------------------------+
| R1  | Document ID Generation   | abs(hash(path)) % 1000000 | Deterministic UUID v5 or SHA-256      |
| R2  | Region ID Counter Format | {counter:03d} (max 999)   | {counter:04d} or UUID token suffix    |
| R3  | Topological Sort Pop     | list.pop(0) (O(N))        | collections.deque.popleft() (O(1))    |
| R4  | Graph Edge Deduplication | Set lookup on tuple       | Direct Adjacency Map in Builder       |
+----------------------------------------------------------------------------------------------------+
```

### 4.1 Refactor R1: Deterministic Document ID Generation
- **Problem**: `GeometricLayoutZoner.segment_layout()` generates document IDs using `abs(hash(document.source_path)) % 1000000`, producing a 6-digit integer string (`layout_doc_123456`). Under the birthday paradox, collisions occur with 50% probability after only ~1,200 documents.
- **Mandated Fix**: Replace with deterministic **UUID v5** using a dedicated MechAI namespace and the resolved source path (or SHA-256 hash of document content).
- **Impact**: Zero contract changes (`document_id` remains a `str`); eliminates collision risk across millions of documents.

### 4.2 Refactor R2: 4-Digit Region Identifier Padding
- **Problem**: Region IDs are formatted as `f"reg_p{page}_{counter:03d}"`. Highly complex exploded diagrams or dense parts matrices with over 999 regions on a single page will overflow formatting alignment (`reg_p1_1000`), breaking alphabetical sort invariants.
- **Mandated Fix**: Update region ID formatting to `f"reg_p{page}_{counter:04d}"` (supporting up to 9,999 regions per page).
- **Impact**: Prevents sort order corruption on mega-pages.

### 4.3 Refactor R3: Topological Sort Queue Optimization
- **Problem**: `ReadingOrderGraph.topological_sort()` uses Python `list.pop(0)` for queue extraction, resulting in $O(N)$ memory shifts per pop and $O(N^2)$ overall queue drain time.
- **Mandated Fix**: Refactor the topological sort work queue to use `collections.deque` with `popleft()`, restoring true $O(V + E)$ topological traversal.
- **Impact**: 10x throughput improvement on dense, complex diagram pages.

### 4.4 Non-Blockers Explicitly Cleared for Phase 3
- *Adjacency list caching on frozen `ReadingOrderGraph`*: The frozen tuple representation is fast enough for per-page graphs ($N \le 100$). Internal dict indexing can be deferred to RFC-023.
- *Decoupling `contracts/__init__.py` namespace*: The aggregated export file causes no runtime performance degradation and provides a clean single-point import surface for Phase 3 developers.

## 5. Technical Debt Register

A prioritized register of known technical debts across Stages 1.0 to 2.1:

```
+----------------------------------------------------------------------------------------------------+
|                                    TECHNICAL DEBT REGISTER                                         |
+----------------------------------------------------------------------------------------------------+
| Priority | Item Description                   | Module / Area      | Impact | Effort | Milestone   |
+----------+------------------------------------+--------------------+--------+--------+-------------+
| CRITICAL | Document ID modulo hash collision  | layout/zoner.py    | HIGH   | LOW    | Pre-Phase 3 |
| HIGH     | Quadratic list.pop(0) in topo sort | ordering/graph.py  | MED    | LOW    | Pre-Phase 3 |
| HIGH     | Fixed 999 region counter limit     | layout/zoner.py    | MED    | LOW    | Pre-Phase 3 |
| MEDIUM   | Hardcoded confidence calibration   | layout / ordering  | MED    | MED    | v1.1        |
| MEDIUM   | Triple data materialization        | contracts/pipeline | MED    | HIGH   | v1.4        |
| MEDIUM   | English-only regex in zoner        | layout/zoner.py    | LOW    | MED    | v2.0        |
| LOW      | Linear scan in graph get_node()    | ordering/graph.py  | LOW    | LOW    | v1.1        |
| LOW      | Fixed US Letter fallback margins   | layout/zoner.py    | LOW    | LOW    | v1.1        |
+----------------------------------------------------------------------------------------------------+
```

### Debt Prioritization Details

#### Priority 1: Critical (Must Resolve Immediately)
1. **Document ID Modulo Hash Collision**:
   - *Impact*: High. Risk of overwriting intermediate layout artifacts in shared data lakes.
   - *Effort*: Low (< 1 hour).
   - *Target*: Pre-Phase 3 Refactor R1.

#### Priority 2: High (Resolve Before Large-Scale Benchmarks)
2. **Topological Sort Queue Complexity**:
   - *Impact*: Medium. CPU bottleneck on pages with hundreds of small callouts.
   - *Effort*: Low (< 1 hour).
   - *Target*: Pre-Phase 3 Refactor R3.
3. **Region ID Format Overflow**:
   - *Impact*: Medium. Lexicographical sorting discrepancies on dense exploded views.
   - *Effort*: Low (< 1 hour).
   - *Target*: Pre-Phase 3 Refactor R2.

#### Priority 3: Medium (Address in Maintenance & v1.x Releases)
4. **Hardcoded Epistemic Confidence Constants**:
   - *Impact*: Medium. Confidence scores (0.95, 0.92, 0.88) reflect heuristic estimates rather than empirical Bayesian calibrations against ground-truth datasets.
   - *Effort*: Medium (requires validation against annotated benchmark sets).
   - *Target*: Milestone v1.1 / RFC-021.
5. **Triple In-Memory CIR Materialization**:
   - *Impact*: Medium. Memory overhead when processing multi-thousand-page manuals in batch mode.
   - *Effort*: High (requires streaming generator architectural shift).
   - *Target*: Milestone v1.4 / RFC-023.
6. **English-Centric Keyword Patterns in Layout Zoner**:
   - *Impact*: Low for English OEM manuals; prevents out-of-the-box extraction of German/Japanese native manuals.
   - *Effort*: Medium.
   - *Target*: Milestone v2.0 / RFC-022.

#### Priority 4: Low (Code Quality & Micro-Optimizations)
7. **Linear Scan in `ReadingOrderGraph.get_node()`**:
   - *Impact*: Negligible for $N < 100$; minor overhead during graph inspection.
   - *Effort*: Low.
   - *Target*: Milestone v1.1.
8. **Fixed Fallback Page Dimensions**:
   - *Impact*: Negligible since PyMuPDF extracts exact page dimensions from PDF headers; only triggers on malformed pages with 0 width/height.
   - *Effort*: Low.
   - *Target*: Milestone v1.1.

### 6.1 RFC-018: Optical Character Recognition (OCR) Subsystem
- **Purpose**: Provide a secondary extraction backend for scanned raster PDFs (legacy pre-2000 workshop manuals). Introduces an OCR coordinator stage that renders pages to high-DPI bitmaps, performs layout-aware text recognition, and synthesizes standard `ParsedWord` tokens with exact bounding boxes, integrating transparently into the frozen `ParsedDocument` contract.

### 6.2 RFC-019: HTML / XML / Web Service Manual Adapters
- **Purpose**: Ingest OEM documentation delivered via web platforms (e.g., BMW TIS, Tesla Service Portal, GM Service Information). Converts DOM structures and SVG wiring diagrams directly into `ParsedDocument` and `LayoutCIR` primitives without intermediate PDF rendering.

### 6.3 RFC-020: Distributed Multi-Node Pipeline Orchestration
- **Purpose**: Enable massive horizontal scaling across multi-node clusters using Celery/Ray/Kafka. Implements partitioned job dispatching, distributed object store caching (S3/MinIO), and node-level fault-tolerant checkpointing to process 1,000,000+ manuals with zero operator intervention.

### 6.4 RFC-021: Empirical Confidence Calibration Framework
- **Purpose**: Replace heuristic confidence assignments with calibrated Bayesian probabilistic scoring. Uses a golden benchmark dataset of 5,000 manually verified manual pages to tune spatial, typographical, and classification probabilities against empirical precision-recall curves.

### 6.5 RFC-022: Multilingual Document Processing Engine
- **Purpose**: Extend layout intelligence, safety keyword detection, and procedural step classifiers to support non-English OEM documentation (German, Japanese, French, Spanish, Chinese). Introduces localized regex dictionaries, multilingual token normalizers, and language-specific reading order rules.

### 6.6 RFC-023: High-Performance Memory & Streaming Optimization
- **Purpose**: Redesign the internal pipeline transport to support streaming page-by-page CIR generation with memory-mapped disk buffers. Eliminates eager full-document memory allocations, allowing a standard worker to process 5,000+ page heavy machinery manuals within a strict 512MB RAM ceiling.
